Performance

How the AtomAttr browser engine turns attributes into CSS, what that costs, and how to measure it yourself.

AtomAttr is a runtime engine. There is no compile step in the browser build: the engine reads attributes while the page runs and writes the CSS they need. This page explains that lifecycle, shows measured costs, and covers the trade-offs.

How the engine works

  1. Start. The engine starts as soon as the script runs, even while the page is still being parsed. Load the browser build with a normal script tag in <head> (not defer) so elements are styled as the parser adds them.
  2. Parse. For each supported attribute it parses the prefix (md-, hover-, dark-, cq-md- and so on), the property and the value. The parsed result for each attribute name and value pair is cached, so a value that appears on a thousand elements is parsed once.
  3. Generate. It builds the CSS declarations and inserts one rule into a single <style id="atomattr-generated"> element with insertRule. Each attribute and value pair is handled once, so p="4" on a thousand elements produces one rule.
  4. Order. Rules are inserted in cascade order, not discovery order: base rules first, then states, then breakpoints from small to large, then container breakpoints. Within a group, broad shorthands (p) come before the longhands they overlap (px, pt). The result therefore does not depend on which attribute the page happened to use first.
  5. Observe. A MutationObserver watches the document. Added subtrees and changed attributes are collected and processed together in the next animation frame, before the browser paints them.

Three consequences follow. The stylesheet grows with the number of distinct attribute values you use, not with the number of elements. Rules are not removed when an attribute disappears; they stay until the page is closed or you clear them. And switching between light and dark does not rebuild anything: colours resolve through CSS variables and dark- rules are scoped to html.dark.

Measured costs

These numbers come from headless Chromium on a shared virtual machine, so treat them as relative, not absolute: a real phone will be slower. The test page gives every element ten attributes (spacing, a breakpoint, light and dark colours, a hover colour, radius, gap, font size, text colour and margin) drawn from 97 combinations, which produces 68 rules. Each figure is the median of several runs and measures a synchronous scan of the whole page with refreshAtomAttr.

The speed-up comes from the parse cache: most pages repeat the same values constantly, so almost every attribute skips the parser. Costs that are dominated by the browser did not change. Toggling dark mode on a 50,000-element page takes roughly the same time in both versions, because it is the browser recalculating styles. Changing an attribute on an element costs about the same as before.

The test page repeats values heavily. A large real app with a wider range of values creates more rules, and a page whose elements are all different gets less from the cache. Memory use, low-end phones and server rendering have not been measured.

Trade-offs

  • Runtime generation needs no build step and works with markup built at any time, including content from a CMS. The cost is the work the engine does in the browser at startup.
  • Build-time generation tools remove that startup work but need a build step and must know every value in advance. AtomAttr does not currently offer a build-time extractor.
  • Content Security Policy. The engine adds rules to a style element, so a strict style-src policy must allow it. Test your policy before shipping.
  • Server rendering. The engine needs a DOM, so start it in the browser only.

Practical guidance

  • Keep values consistent. Reusing p="4" is free; dozens of one-off values each create a rule.
  • Avoid changing the same attribute on many elements every frame. Use a CSS transition or animation instead.
  • Call refreshAtomAttr(container) only when you change markup in a way the observer cannot see.

Measure it yourself

Create an HTML file next to the browser build, open it in your browser, and read the result. Change the counts to match your pages.

HTML
<script src="./dist/atomattr.min.js"></script>
<div id="root"></div>
<script>
  const root = document.getElementById('root');
  let html = '';
  for (let i = 0; i < 10000; i++) {
    html += `<div p="${(i % 8) + 1}" bg="red-500" rounded="xl"><span text="white">Item ${i}</span></div>`;
  }
  root.innerHTML = html;
  const start = performance.now();
  AtomAttr.refreshAtomAttr(document.body);
  console.log('scanned in', Math.round(performance.now() - start), 'ms');
</script>

Run it several times, on the devices you care about, and compare results rather than trusting a single number.

Skipping the runtime cost

If you would rather pay no per-page cost at all, build mode generates the same CSS ahead of time and ships it as a stylesheet, with no engine script in the browser.
