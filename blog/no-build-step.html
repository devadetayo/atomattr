Why We Ditched the Build Step

What you get, and what you give up, when styling needs no compiler.

DdevadetayoAtomattr

"No build step" is easy to say and easy to oversell. This post spells out what it actually means for Atomattr, what gets simpler, and what you should still think about.

What the build step usually does

Compile-time utility systems scan your source files for class names, generate a stylesheet containing only what you used, and ship that file. It is an excellent model, and it needs a toolchain: a compiler or CLI, a config, a watch process in development, and a pipeline step in CI.

What Atomattr does instead

The engine runs in the page. It reads the attributes that are actually present in the DOM and generates the matching rules on the spot. There is no scan of your source files, because the browser already holds the finished markup.

  • Drop-in. A static HTML file, a CMS template, a CodePen or a docs page can use it with one stylesheet and one script.
  • No config to sync. Values come from built-in scales and semantic colors; you can override colors through CSS variables such as --aa-color-primary.
  • Dynamic content just works. HTML inserted at runtime is styled as soon as the observer sees it.
  • Only what is used. Rules are created per attribute and value, and cached, so an unused value never becomes CSS.
html
<!-- inserted later by your own script, still styled -->
<script>
  document.body.insertAdjacentHTML(
    "beforeend",
    '<p text="success" font-weight="700">Saved</p>'
  );
</script>

What you give up

A runtime has real costs, and it would be unfair to hide them:

  • JavaScript is required. Without it, attribute styles do not apply. Content stays readable, but unstyled.
  • Work happens on the visitor's device. The engine does a pass over the page and generates rules. For typical pages this is small, but measure it on yours rather than assuming.
  • Possible flash of unstyled content. Place the script in the head with defer and keep above-the-fold structure simple, or hide the body until the first pass completes.
  • Script weight. The engine is a one-time download that the browser caches. Check the current size in the distributed file.
Check this for your projectIf SEO-critical pages, strict content security policies or no-JS environments matter to you, test them before committing. A runtime engine suits apps, tools, prototypes, docs and internal sites very well; it is a poorer fit when styles must exist before any script can run.

A sensible way to adopt it

  • Start with one page or one component and load the script with defer.
  • Put layout that must not shift (height, grid columns) in attributes, so the first pass settles it immediately.
  • Open the page with the network throttled to see the real first paint.
